# compliance/ — 标准与专利基线（本地材料，元数据入库）

目的有两个，缺一不可：

1. **实现期参照**：写 kernel、写测试、写文档时能查到"权威怎么说"；
2. **交付期证据链**：最终的 Sphinx 要有一页能回答"你遵循了哪些标准、依据是什么、哪些没做"。这一页的内容必须由本目录的元数据**生成**，不允许手写（同 `claim-basis` 的原则）。

## 目录

```
compliance/
├── README.md                 # 本文件：规则与免责声明
├── standards.md              # 标准清单（人读）
├── claims.md                 # 每条对外宣称 → 对应检查名 + 证据 id（草稿）
├── gaps-<date>.md            # 按行业的"答案卡"（问什么→看什么证据→能给什么→缺口→能说/不能说）
├── dl/                       # 实际下载的材料（PDF/XML/仓库快照；**不入 git**）
├── metadata/standards.json   # 标准清单（机读，Sphinx 从这里生成页面）
├── metadata/schema.json      # 记录格式
├── patents/INDEX.md          # 专利检索台账（**空表 + 检索策略**）
└── BLOCKERS.md               # 需要人去获取的付费材料
```

> 这个布局是照 `~/Projects/zc0718/foc/workspace/compliance/` 抄的：那边有 `claims.md`、`dl/`（AUTOSAR C++14、SEI CERT C、MISRA C++ 2023、IEC 61508-7、ISO 26262-8/-10、NASA-STD-8719.13/8739.8、JPL C 标准、FMI 2.0.5 等）和一份由 `render_gaps.py` 生成的八行业答案卡。**那份答案卡的组织方式才是关键**，不是材料本身。

## 行业答案卡的六问（照 foc）

1. 客户会问什么？
2. 他们真正看的证据是什么？
3. 我们今天能给什么？
4. 缺口是什么？
5. 能说的话（准确率用句子）
6. **不能说的话**（边界）

对本工程，建议先做四张：**通用嵌入式 / 工业（IEC 61508 链，不宣称 SIL）/ 家电（IEC 60730 附录 H）/ 汽车（ISO 26262，按需）**。机械、机器人、轨交这类整机安全归属集成商，直接写"不承担"。

## 三条硬规则

1. **不得凭记忆写编号**。任何标准号、专利号、版本年份都必须有**本地文件或可访问 URL** 作为依据；`metadata/standards.json` 的每条都带 `source_url` 与 `verified_at`。
2. **付费材料进 `BLOCKERS.md`**，状态标 `blocked`；不阻塞编码，只阻塞"对外宣称遵循"。
3. **声称"符合 X"必须同时有**：(a) 本地材料，(b) 一条可执行的检查（测试/门禁），(c) `gaps.md` 里写明未覆盖的部分。三者缺一，`gate/claim` 视为无依据。

## 免责声明

`patents/` 里的条目是**技术检索台账**，不是法律意见。本文件不判断有效性、不判断侵权、不提供规避设计结论。任何专利结论都需要法务或有资质的人复核。
