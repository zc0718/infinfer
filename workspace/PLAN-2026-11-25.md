## 0. 结论摘要

0. **能不能"拿到新仓就开工"**：本文 + `KICKOFF.md` 可以。缺口与三处纠正见 **§11**（模板门禁只有 5 条、`metadata` 必填 6 项、模板没有 agent 入口文件）。
1. **命名**：见 §0.1。名字只决定三件事——C 符号前缀、Conan 包名、目录根名——所以它必须在 P0 之前定死，之后改名成本指数上升。
2. **这条路线成立**：参考仓的代码在补上 SMT 的 include 路径后 **32/32 个 TU 零诊断编译、链接后可运行**（已实测），所以新工程是"把已有实现按新契约重排 + 补齐"，不是从零重写。但注意：**新仓不做向后兼容**（无历史消费者），旧符号不进新库。
3. **真正的工作量不在"迁移平台"**，而在三件"框架级"的事：
   - **把 kernel 从 runtime 里剥出来**（现在 `ie_conv2d.c` 同时承担"算子语义"和"数值循环"，两者混在一起，没法给同一算子接不同平台实现）；
   - **建立"参考实现 = 唯一真理源"的差分测试骨架**（所有向量实现都对着它验，跨平台一致性才有判据）；
   - **把宣称变成可复算的证据**（README/Gallery 的每一格 ✅ 指向一条 CI 产物）。
4. **foc 的可复制部分**（也是我们唯一该抄的部分）：**门禁设计**（`.github/project/*.py` 42 个 gate、每个 gate 必须能"红"）、**claim→evidence 链**、**gaps 清单文化**、**测试量级**（961 个用例 / 覆盖率写进 metadata 当门禁）。不可复制部分：foc 的物理模型与上板台架。
5. **QEMU 正确的用法**：它能证功能/鲁棒性/ABI，**不能证性能**。性能必须另有真板或 FVP 数字，并且必须写进 `gaps.md` 说清"这不能证明什么"（§3.2）。
6. **体裁（genre）**：本工程**不是"推理库"**，而是"**可微嵌入式计算图运行时**"——同一张图有三种执行模式（`EVAL` / `GRAD` / `STEP`）与一类显式状态（KV cache / RNN state / 积分器）。纯推理是它的**一个子集**：不链接 backward 时零成本（§2.3）。这条决定了四阶能力阶梯（C1→C4）与语言选择（§3.4），也是本计划与 TFLM/CMSIS-NN 拉开差异的地方。

## 2. 目标架构

### 2.1 分层（核心设计）

```
┌──────────────────────────────────────────────────────────────┐
│ L4 应用形态：分类/检测 · 语音 · 生成 · 自适应控制(PID)       │
│    （不在本仓，但它们反过来约束 L2 的能力集合）              │
├──────────────────────────────────────────────────────────────┤
│ L3 证据与文档：census / claim-basis / benchmark / audit      │
├──────────────────────────────────────────────────────────────┤
│ L2 图运行时：图解析 · 派发 · 融合 · 后处理 · backend 装配     │
│    执行模式（§2.3）：EVAL ┃ GRAD ┃ STEP                      │
│    张量区（§2.3）：workspace(复用) ┃ activation(保留) ┃ state(持久) │
├──────────────────────────────────────────────────────────────┤
│ L1 内核：纯函数，只认「指针 + 长度 + dtype + quant」         │
│    scalar(参考/oracle) │ x86 │ arm │ arm_m │ rvv │ 厂商(可选) │
│    每个内核 = (dtype × quant) 的模板实例，由矩阵表生成(§3.5)  │
├──────────────────────────────────────────────────────────────┤
│ L0 Port：唯一的平台宏面（restrict/inline、属性、日志、断言） │
└──────────────────────────────────────────────────────────────┘
```

**与现状的差别**：当前 L1 与 L2 同处 `src/layers/*.c` 中（一个文件既是"算子的 shape 语义"又是"内层循环"），L0 散落在 `ie_def.h` + `smt_api.h` 两处各定义一份（`IE_RESTRICT` vs `SMT_RESTRICT`）。合并后**一个算子 = 一份语义（L2）+ N 份实现（L1）**。

### 2.2 十一条不变量（gate 会强制）

1. **INV-1**：`include/` 下不得出现任何架构专有头（`arm_neon.h`、`immintrin.h`、`riscv_vector.h`）或任何厂商库头。架构代码只在 `src/kernel/<arch>/`。
2. **INV-2**：每个 kernel 必须有一份 `scalar` 实现，且**它是唯一的正确性定义**；其它实现只准通过差分测试证明等价。
3. **INV-3**：kernel 签名不得包含 shape/stride（只 `const T* + n`）；shape 语义只存在于 L2。
4. **INV-4**：量化是一等公民：`dtype × {none, per-tensor, per-channel}` 的组合在契约里显式枚举，缺一即编译期/门禁报错。
5. **INV-5**：主包（`include/` + `src/`）不得依赖任何测试库或厂商加速库；厂商后端只能是**可选装配单元**（Conan option）。
6. **INV-6（新鲜 clone 自洽）**：`git clone` + `conan create .` 在**没有任何本地配方、没有私有 remote、没有 `workspace/`** 的机器上必须构建成功（自动退化为 scalar-only）。CI 的每一道门禁都必须能在这种环境下运行；依赖 `workspace/` 的步骤必须**显式 skip 并打印原因**。
7. **INV-7（平台准入）**：一块板子进入 README/`capabilities.rst` 矩阵的充要条件是——① 用 **house toolchain**（`arm-toolchain` / `rv-toolchain`）能构建出产物；② 在 QEMU 或实机上跑通同一套 KAT。两条缺一，就不许写。
8. **INV-8（状态是一等公民）**：持久状态（KV cache / RNN·LSTM state / PID 积分器）必须是**显式声明的张量区**，不得藏在算子的静态变量里；且引入状态不得让 `EVAL` 路径多出一次动态分配。
9. **INV-9（梯度可选但不可伪造）**：`GRAD` 模式的反向内核必须由 scalar 前向推导，并与**有限差分**对齐（相对误差 ≤ 1e-4）；不提供梯度的内核必须在矩阵表里显式标 `no-grad`，不得静默复用前向。
10. **INV-10（矩阵单一来源）**：`dtype × quant × tier` 的合法组合**只在一张矩阵表里声明**；模板实例化、census、parity 桩、文档表格**全部由它生成**，手写的第二份清单视为违规。
11. **INV-11（根目录白名单）**：仓库根只允许模板给定条目 + `include/ src/ test_package/ benchmark/ docs/ workspace/`。新工具默认进 `workspace/`；"CI 必须执行"优先改成"产物入库 + CI 只验证"，不得为了一个脚本新增顶层目录。

### 2.3 体裁的技术落点：三档执行模式 + 三类张量区

> 这一节回答"它到底是不是推理库"，也是 C1–C4 能力阶梯的定义来源。

| 模式 | 用到的层 | 内存模型 | 典型形态 | 额外成本 |
|---|---|---|---|---|
| `EVAL` | 前向 | workspace **时分复用**（现有 offset table） | 分类/检测/语音推理 | **零** |
| `GRAD` | 前向 + 反向 | activation 必须**保留**到反向用完（按层 arena） | 3 层 MLP 的 BP、小参数集在线适应 | 内存 ≈ ×层数 |
| `STEP` | 反向 + 优化器 | 参数区 + 动量区 **持久** | 自整定 PID、tiny fine-tune | 参数 ×2~3 |

**三条判断（写给 leader）**：

1. **三种模式不是三个产品，而是同一张图的三种链接方式**：不链接 backward → 二进制里没有梯度代码（link-time 裁剪），纯推理客户不受任何惩罚。
2. **它决定了内存模型的第三条腿**：现在是"复用"（offset table），`GRAD` 需要"保留"，`STEP` 需要"持久"。这三条腿必须在 L0 就分好，**不能事后加**——这是 `gate/budget` 的记账对象，也是参考实现中尚未引入的概念。
3. **能力阶梯（每级可独立交付、独立宣称）**：

| 阶 | 能力 | 支撑什么 | ROI 判断 |
|---|---|---|---|
| **C1 纯推理** | `EVAL` | 分类/检测/语音定长推理 | 必需（本 plan 的 P1–P5） |
| **C2 有状态推理** | `EVAL` + `state` | 流式语音、逐 token 生成、PID 的 I/D 项 | 必需（否则连 PID 都表达不了） |
| **C3 小模型 BP** | `GRAD` + `STEP` | 参数自更新、在线自整定 | **差异化**（TFLM/CMSIS-NN 不做） |
| **C4 SoC 规模** | C1+C2+多线程/大模型 | 大模型/生成式（Linux） | 跟随（Linux 上打不过 XNNPACK，价值在"同一张图 + 同一套证据"） |

> **范围控制**：C1→C4 串行，C3/C4 必须在 C1/C2 交付后按需求启动（§6 第 12 条）。这是"体裁扩张"不变成"烂尾"的唯一保险。

**模态是无关的（重要）**：L1/L2 里没有任何"图像"概念——只有 shape / dtype / quant / stride。所以语音、IMU、振动、时序用的是同一套东西。但上语音应用时要补三件事（写进 `capabilities.rst`，不能只活在口头）：

| 需求 | 现状 | 处置 |
|---|---|---|
| 1-D 张量 | 4D 联合体可以表达：`[1,1,T,C]`（`nhwc` 的 h=1） | 不改契约 |
| 1-D 算子 | **无** `conv1d`/`dwconv1d`（`layers.md` 里 Conv1D 标 🏗️ 是对的） | 若模型是 T×F 谱图（2D conv）则 C1 直接能跑；纯波形模型需在 C1 后补 1D 算子族 |
| **流式** | `EVAL` 每次重建张量池，无隐状态 | ASR 几乎都是流式 → **真正卡点是 C2（`state` 区）**，不是算子 |
| 特征前端（MFCC/FBank） | 不属神经网络算子 | 第一版**明确排除在库外**（写进 `guides/audio.rst` 的 out-of-scope），或后续作为 SMT 的 DSP 内核引入 |
| 语音后处理（CTC/argmax over time） | 现有后处理只有分类/YOLO | 作为示例提供，不进核心 |

> 一句话：**同一个引擎既能跑图像也能跑语音，但"定长片段"靠 C1，"实时流式"必须 C2**。

**边界：它不是"推训一体框架"**（这个措辞会把客户预期带偏，必须在文档里写死）：

| 维度 | 本工程（C3 上限） | 真正的"推训一体"（PyTorch/TF） |
|---|---|---|
| 数据 | 单样本 / 小 batch 的**在线**更新 | 数据集、epoch、shuffle、DataLoader |
| 参数范围 | 少量层或最后一层（≤ 10k 参数） | 全参数 |
| 反向 | **受限反向**：只为已实现的内核提供手工反向 | 通用 autograd（任意自定义算子自动求导） |
| 优化器 | SGD(+momentum)，最多加 Adam | AdamW/AdaFactor + LR schedule + 混合精度 |
| 内存 | 激活保留 ≈ ×层数，MCU 上只能是小模型 | 默认就有 |
| 明确不做 | QAT、分布式、大模型微调、checkpoint 管理 | — |

所以准确的体裁是：**"推理 + 有限在线适应"（inference + on-device adaptation）**，不是训练框架。这个界定直接决定了下一节 ADR-004 的结论：**训练侧不需要任何交换格式**。

## 3. 前置技术判断（ADR 组）

### 3.1 ADR-001 · 加速后端选型：厂商无关的三层梯度

> 这一节是**决策记录**，不是调研笔记。决策错了后面全错，所以每个结论都标了依据。

**目标函数（单一）**：在"只能用 house toolchain 构建"的约束下，用**一套代码**覆盖尽可能多的板子，且**任何一块板子的"能跑"不得以绑定某个厂商库为前提**。

**约束（已核实）**

| 约束 | 事实 | 来源 |
|---|---|---|
| ARM 工具链 | `arm-toolchain` 的 train：`11.3/12.3/13.3/14.3/15.2.rel1`；**本机已装 11.3.1**，`arm-none-eabi` 覆盖 m0…m85，另有 `aarch64-none-elf` 与 Linux A 类 triplet | `arm-toolchain/conanfile.py:22-53`；本机 Conan 缓存 |
| ARM MVE 头 | **本机 11.3.1 工具链自带 `arm_mve.h`**（实测路径 `~/.conan2/p/arm-t2e40a35dc5206/p/…/11.3.1/include/arm_mve.h`） | 实测 |
| RV 工具链 | `rv-toolchain` 是**模板式配方**：`conandata.yml` 已收录 `11.3 / 12.3 / 13.3 / 14.3 / 15.3.rel1` 五个 train，**可按需构建任意一个**（改 `version` 即可）；裸机走 xpack `riscv-none-elf`，Linux RV64 走 Bootlin glibc | `rv-toolchain/README.md`、`conandata.yml` |
| **RVV 的 train 选择** | ratified RVV 1.0 的 `riscv_vector.h` 需 **GCC ≥ 13**。⇒ 本项目 RV **主线取 `14.3.rel1`**（intrinsics 成熟、自动向量化最好）；`12.3.rel1` 只作"老板子兼容抽查"且仅跑 scalar 档；`11.3` 不用于本项目 | 编译器事实 + 配方可任选 train；P0.6 实测头文件 |
| 厂商约束 | 需要定制 GCC 的芯片（如中科蓝讯）不能进矩阵；沁恒类（原厂 SDK 与我们的 `rv-toolchain` 双通）可进 | 团队既定方针 |

**候选库清单（核验日 2026-11-25）**

| 库 | 绑定对象 | 能不能跨厂商 | Conan Center | 活跃度 | 判定 |
|---|---|---|---|---|---|
| **CMSIS-NN** | Cortex-M（MVE/DSP），A 类官方建议改用 ACL/XNNPACK | ARM 内部通用 | ❌ 404 | v8.0.0 / 2026-08，未 archived | `arm_m` 档的**可选**加速 |
| **CMSIS-DSP** | ARM 通用 DSP 原语 | ARM 内部通用 | ❌ 404 | 1141★ / 2026-11 | 可选，非必需 |
| **NMSIS** | Nuclei 核的 DSP/P 扩展 | **❌ 锁 Nuclei** | ❌ 404 | 96★ / 2026-06 | **不做必需**，只做插件示例 |
| **CSI-NN2** | 玄铁 C906/C910（RVV 0.7.1/1.0） | **❌ 锁 XuanTie** | ❌ 404 | 105★ / 2026-02 | **不做必需**，只做插件示例 |
| **PULP-NN** | PULP/RI5CY（Xpulp） | ❌ | ❌ 404 | 99★ / **2023-10 停更** | 不纳入，写 gaps |
| **XNNPACK / ACL** | ARM64 Linux SoC | 只在 ARM64 | 部分有 | 活跃 | SoC 可选插件 |

**为什么"选一家 NN 库通吃 RISC-V"在技术上不成立**（这是你最担心的点，值得写清楚）

1. RISC-V 上**唯一跨厂商的加速面是 RVV**（ ratified 1.0）。NMSIS 的加速依赖 Nuclei 的 DSP/P 扩展，CSI-NN2 的加速依赖玄铁自己的 RVV 版本——**在没有这些扩展的核上，它们退化为标量，却仍然会"看起来被支持"**，这比"不支持"更不易察觉（平台矩阵要避免的正是"能跑 ≠ 能用"）。
2. **RV32 上基本没有 RVV**（Zve32x 也稀少），所以 RV32 的现实答案是 **scalar + 强迫自动向量化**，不存在"选个库就快"的选项。
3. RVV 自身也分裂： ratified 1.0 vs C906 的 0.7.1 vs Xpulp 的 SIMD，**三套 ISA 不共代码**；只有 1.0 能跨厂商。

**决策：三层梯度（任一层缺失都不影响"能跑"）**

| 层 | 作用 | 何时编译 | 缺失后果 |
|---|---|---|---|
| **L-k0 `scalar`** | 唯一定义正确性的参考实现 | 永远 | 不允许缺失（INV-2） |
| **L-k1 `autovec`** | 同源 C，`-O3 -ftree-vectorize`，让编译器去向量化 | 永远（除调试） | 只影响速度 |
| **L-k2 `isa`** | 手写 intrinsics：`arm_neon.h` / `arm_mve.h` / `xmmintrin.h` / `riscv_vector.h` | 由 `settings.arch` 选定 | 退到 L-k1 |
| **L-k3 `vendor`**（可选） | CMSIS-NN / CSI-NN2 / NMSIS / XNNPACK | Conan option 打开时 | 退到 L-k2 |

**两条硬则**：
- "能不能跑"只由 L-k0 决定； vendor 库**只影响速度**，不承担任何"能跑"承诺。
- 关掉 vendor option 后，产物符号表里**不得出现**任何厂商前缀（`nm` 校验，`gate/vendor`）。

**平台准入判据**（已升为 INV-7 + `gate/targets`）：house toolchain 能构建 + QEMU/实机跑通 KAT，两条齐备才允许写进矩阵。按此条：中科蓝讯类（定制 GCC）出局；沁恒类纳入。

### 3.1.1 Conan 配方格式（按官方格式，照仓内范例）

两类配方，两种布局，都不能自创：

| 类型 | 范例（本机已存） | 布局 | 要点 |
|---|---|---|---|
| **库配方**（厂商加速库） | `HeT-FTI/mnn`、`HeT-FTI/opencv` | 类 conan-center-index：`<pkg>/config.yml` + `<pkg>/all/{conanfile.py,conandata.yml,test_package/}` | `config.yml` 做版本→folder 映射；`package_info()` 填 `cpp_info`；`test_package/` 必须能单独跑 |
| **工具链配方** | `HeT-FTI/arm-toolchain`、`HeT-FTI/rv-toolchain` | 单 `conanfile.py` + `conandata.yml`（版本→triplet→`sha256`）+ `profiles/` + `test_package/` | 以 **build requirement** 创建（否则 `settings_target` 为空）；**所有下载件必须带 sha256 钉死** |

**最小验收**：`conan create <recipe> --build=missing` 在干净 cache 下能过；`test_package` 里真的 include 一次并使用一个符号；关掉 option 时 `conan create` 仍能过（INV-6）。

**可用性三条**：
1. **必须是 option，不是依赖**：`metadata.dependencies` 四桶表达"永远需要"；厂商库用 **Conan option**（`with_cmsis_nn`、`with_csi_nn2`）+ 条件 `self.requires(..., transitive=False)`。fcpp v0.3.11 的 recipe 目前只有 `shared/fPIC` 两个 option（`conanfile.py:110`），**需扩展**——P0.3 的明确改动项。
2. **必须过 `deps_gate`**：厂商库不得进入主包 include 路径（INV-1/INV-5）。
3. **配方不进版本库**（按你的要求放 `workspace/conan/recipes/`），所以 `conandata.yml` 只留需求行 + 版本，分发靠私有 remote `hetai`；拿不到时按 INV-6 退化为 scalar-only。

### 3.2 用 QEMU 把"软件端可靠性"推到极致——可以，但要写清边界

| QEMU 能证明 | QEMU 不能证明 | 对应门禁 |
|---|---|---|
| 编译/链接/ABI 正确性 | 周期数、真实性能 | `gate/build`, `gate/apicontract` |
| 功能正确性（同一 KAT 在 M3/M4F/M7/M55/RV32/RV64/Linux 上输出一致） | 缓存/总线/中断延迟 | `gate/kat` |
| 内存越界、未对齐访问、UB（配 ASan/UBSan 的 host 侧 + QEMU 侧） | 功耗、温度、电气 | `gate/sanitize` |
| 内存不足路径（把 QEMU 机器 RAM 调到刚好不够，断言返回码而不是崩溃） | 外设真实时序 | `gate/budget` |
| 裸机启动、链接脚本、`.bss/.data` 尺寸 | MVE/自定义扩展的真实吞吐 | `gate/size` |
| 多核/线程语义（SoC 侧） | 与 CMSIS-NN 的真实性能比 | — |

**做法**：
- `qa/qemu/` 里每个目标一个 `board.json`（QEMU 机器名、RAM、CPU 特性）+ 一个 runner 脚本；
- 目标清单：`netduinoplus2`(M4F)、`mps2-an385`(M3)、`mps2-an500`(M7)、`mps3-an547`(M55/MVE)、`virt`(RV32/RV64)、`qemu-aarch64` (Linux SoC 用户态)；
- 性能另立一档：**FVP/真板**。CMSIS-NN 自己就在 CI 里跑 FVP 测试，可以照抄其 workflow 形状；**但任何 FVP/QEMU 数字都必须在 `gaps.md` 标注"模型数，非硅片数"**。
- 一句话写进 `capabilities.rst`：**"QEMU 证明正确，不证明快"**。

### 3.3 architecture-agnostic 且"SoC 无性能短板"怎么兑现

单靠一套 C 循环做不到。必须承认 **kernel 要按 ISA 分档**，并把"选择权"做成两种模式：

| 模式 | 场景 | 机制 | 代价 |
|---|---|---|---|
| **编译期选择** | MCU/裸机 | Conan `settings.arch` + `-mcpu/-march` → 只编一个 tier | 零运行期开销 |
| **运行期选择** | Linux SoC（x86-64/ARM64/RV64 同一个二进制） | `cpuid`/`hwcaps`/`riscv_hwprobe` → 函数指针表（可选 IFUNC） | 一次间接调用 |

**性能验收判据（写死，不许事后调）**：在 4 个档位（x86-64 AVX2、ARM64 NEON、RV64 RVV-1.0、Cortex-M7 DSP）上，自研 kernel 的 conv/dwconv/fc 吞吐 **≥ 对应厂商库（CMSIS-NN / XNNPACK / CSI-NN2）的 70%**，elementwise ≥ 90%。达不到就把该档标进 `gaps.md` 并明示"该平台请接厂商后端"。

**档位与 house toolchain 的对应（这一列是硬约束，不是建议）**

| 档位 | 需要的 ISA | 最低工具链 | 覆盖的核 |

| `scalar` | 无 | `arm-toolchain/11.3.rel1`、`rv-toolchain/14.3.rel1`（主线） | 全部 |
| `x86` (SSE2/AVX2) | SSE2 / AVX2 | 宿主 GCC/Clang | x86-64 |
| `arm_neon` | NEON | `arm-toolchain/11.3.rel1` | Cortex-A（armv7hf / armv8） |
| `arm_m` (DSP) | DSP 扩展（SMLAD/SDOT） | `arm-toolchain/11.3.rel1` | M4/M7/M33/M35P |
| `arm_m` (MVE) | Helium | `arm-toolchain/11.3.rel1`（**实测自带 `arm_mve.h`**） | M55/M85 |
| `rvv` | RVV 1.0 | **`rv-toolchain/14.3.rel1`**（最低 13.3） | C908/C910v2、K1/K60、X280、AX45MPV、UX900 |
| `rv-scalar` | 无（**RV32 的现实答案**） | `rv-toolchain/14.3.rel1`；`12.3.rel1` 仅作兼容抽查 | 全部 RV32/RV64 |

### 3.4 ADR-002 · 实现语言：C11 ABI + C++17 编排 + 单一 C 方言

**决策（三轨，但纪律硬）**：

| 轨 | 范围 | 语言 | 纪律 |
|---|---|---|---|
| **ABI** | `include/infinfer/*.h` | **C11**（`build_cstd="11"`），**不手写 `extern "C"`** | `_Generic` 便利宏必须包在 `#if __STDC_VERSION__ >= 201112L` 里；**类型化函数永远存在**，C99 消费者不得被堵在门外 |
| **编排** | `src/runtime/`、`src/kernel/{x86,arm,arm_m,rvv}/`、`src/backend/` | **C++17 freestanding** | `-fno-exceptions -fno-rtti -fno-threadsafe-statics`；**禁用 STL 容器**（需容器用 `etl`，已在 baremetal 白名单，foc 也在用） |
| **参考内核** | `src/kernel/scalar/` | **C11**（与项目一致，无第二方言） | 没有 `gate/c99`：用户 2026-11-26 质询后撤回——`_Generic` 的红利结构性为零（它属于 ABI 便捷层，且 INV-10 禁止参考体做 dtype 派发），而 `-std=c99` 因 glibc 回退宏**看不见** `_Static_assert`。保留的是**装机头可被 C99 include**（`gate/header_dialect`，有真实消费者）。详见 gaps G-56 |

**C99 → C11 的收益（这是从 C99 升级的唯一理由，必须用得上才升）**：

| 特性 | 用在哪 | 收益 |
|---|---|---|
| `_Static_assert` | kernel 契约、`matrix.yml` 生成的枚举表 | INV-4/INV-10 变成**编译期**错误，而不是运行期/门禁才发 |
| `_Generic` | 只在 ABI 便捷层（`infr_add(a,b,y,n)` → `infr_add_f32`/`infr_add_s8`） | 用户不用写类型后缀；但**不能**用它代替 kernel 矩阵 |
| `_Alignas` / `aligned_alloc` | workspace、SIMD 加载 | NEON/MVE/RVV 的对齐要求少一个隐患 |
| 匿名 union/struct | `IeTensor` 形状联合体 | 少一层命名，可读性 |

**代价**：MSVC 需 `/std:c11`（VS2019 16.8+）；模板的 `C_STANDARD=${BUILD_CSTD}` 已处理（`CMakeLists.txt:158,237`）。**结论（2026-11-26 修订）：升 C11，且不保留第二方言**——上表四条收益没有一条落在参考体上（`_Static_assert` 两种方言下都能用；`_Generic` 属于 ABI 层且 INV-10 禁止参考体拿它做派发；`_Alignas` 是 SIMD 档的事；匿名联合无使用），而 `-std=c99` 又因 glibc 的 `_Static_assert` 回退宏根本看不见那条断言，所以「参考体必须 C99」既不保护东西、也验不到它声称保护的东西。**保留的唯一方言属性是「装机头可被 C99 include」**（`gate/header_dialect`，有真实消费者：客户用自己的编译器 include 我们的 ABI 头）。见 gaps G-56。

**组件图（已对照 fcpp 0.3.11 源码核实）**：`package_info()` 已实现 `_c`/`_cpp` 双组件与 `component_requires` 边的合并，`configure()` 里提前查环。但要拿到"C 内核 + C++ 编排"，**边的方向必须是 `{"infinfer_c": ["infinfer_cpp"]}`（`_c` 依赖 `_cpp`）**：

| 组件 | 包含 | 理由 |
|---|---|---|
| `infinfer_c` | `src/abi/*.c`（只做 C ABI 包装） | 它调 C++ 核心，所以它依赖 `_cpp`（foc 的 `foc_c: [foc_cpp]` 同构） |
| `infinfer_cpp` | `src/runtime/` + `src/kernel/**` + `src/backend/`（**含 scalar 的 `.c`**） | 编排要用 scalar 内核，所以 scalar 必须在 `_cpp` 里，否则**形成组件环** |

> 模板默认按**扩展名**分流（`.c` → `_c`，`.cpp` → `_cpp`，见 `CMakeLists.txt:206-207`），所以要把 `src/kernel/scalar/*.c` 编进 `_cpp`，需要一行 tolerated fork：
> ```cmake
> file(GLOB_RECURSE SCALAR_C CONFIGURE_DEPENDS src/kernel/scalar/*.c)
> add_library(${LIB_NAME}_cpp ${BUILD_TYPE} ${CPP_SOURCES} ${SCALAR_C} ${MODULE_FILES})
> ```
> 这样 scalar 保持真正的 C（而不是改名成 `.cpp` 伪装），且 `exports_sources` 已包含 `src/*`，无需再改。
>
> **执行顺序修正（C15 实测）**：这条 fork 只在 `src/abi/*.c`（C ABI 包装调 C++ 核心）存在时才必需。在那之前把组件边设成 `component_requires: {"infinfer_cpp": ["infinfer_c"]}` 就能让 `_cpp` 调到 `_c` 里的 kernel，**`CMakeLists.txt` 一行都不用改**（对照实验 42/42 绿，见 gaps G-35）。脚手架零改动是默认态，不是待办项。

**为什么不是纯 C、也不是纯 C++**：

| 方案 | 优点 | 致命问题 |
|---|---|---|
| 纯 C99 | 现有代码零迁移；任何核能编 | dtype×quant×tier 的 N×M 只能靠手写复制或宏——**这正是参考实现里 26 个文件直接引用 `buf.pf32` 的对应原因**；而 BP/反向传播几乎不可写 |
| 纯 C++17 | 模板特化、RAII、可微图好写 | 公开头一旦混入 C++，ABI 就锁死在编译器上；MCU 端的异常/RTTI/静态构造全是坑 |
| **三轨（推荐）** | 各取所长：ABI 稳定、MCU 友好、矩阵零成本特化 | 需要纪律，且要能自动判违规 |

**模板真正赚在哪**（这是选 C++ 的唯一硬理由）：`conv2d<dtype, quant, tier>` 一次性写成模板，`if constexpr` 展开平台分支，最后只暴露 `infr_conv2d_s8` / `infr_conv2d_f32` 这样的 C 符号——**N×M 的矩阵变成编译期实例化，而不是手写复制**。

**待验证（P0.6）**：bare-metal 的 `arm-none-eabi` / `riscv-none-elf` triplet 是否带 `libstdc++`。**本机只装了 `arm-none-linux-gnueabihf` 变体，bare-metal 未实测**；但 freestanding 路线本来就不需要 libstdc++（不用 STL），只需确认 GCC 11 在 `-fno-exceptions` 下能正常实例化模板。

**已核实的模板事实（不用再改 metadata）**：

| 事实 | 位置 | 对我们的含义 |
|---|---|---|
| `configure()` 已把 `settings.compiler.cppstd` 强制成 `metadata.build_cppstd`（非 17/20/23 回退 17） | `conanfile.py:216-218` | C++17 选型**无需改模板** |
| `options` 只有 `shared/fPIC` | `conanfile.py:110` | 厂商库必须新加 option + 在 `requirements()` 加条件（P0.3） |
| `requirements()` 逐条 require `conandata['requirements']`，只有 baremetal 交叉时才按 `baremetal_white_list` 过滤 | `conanfile.py:247-258` | 厂商包默认就会在 MCU 交叉时被滤掉——正好符合 INV-5；需要时再显式入白名单 |
| 覆盖率仅宿主：`if(ENABLE_COVERAGE AND NOT CMAKE_CROSSCOMPILING)` | `CMakeLists.txt:262` | 交叉/QEMU 构建不插桩，天然支持"QEMU 只证功能"（§3.6） |
| 单语言项目自动补 `generated/*_placeholder.*` | `CMakeLists.txt:193-203` | `_c`/`_cpp` 任一侧为空也不会构建失败 |

### 3.5 ADR-003 · 评估体系：foc 的 42 个门禁哪些能用

**直接回答 Q1**：foc 的门禁里，**只有"工程治理类"可以直接搬**；"领域正确性类"必须**换 oracle**——foc 的 oracle 是电机物理模型（`plant_reference.py`），infinfer 的 oracle 是**参考框架 + 参考解释器**。

| foc 门禁 | 它防的是 | infinfer 对应 | 处置 |
|---|---|---|---|
| `wired` / `apicontract` / `deps` / `scaffold` / `form` / `guard` / `docfmt` / `docannot` / `docscope` / `docver` / `docshape` / `census` / `guidefull` / `compliance` | 工程治理 | 原样搬 | **直接复用** |
| `plantref` | 实现与独立模型不一致 | **`oracle`：Python 参考解释器 + 与 PyTorch/ONNX Runtime/TFLite 的固定输入输出对比** | 换 oracle，机制照抄 || `fmu` / `pil` | 硬件在环 | **QEMU / 真板在环** | 换目标，机制照抄 |
| `mcdc` | 分支覆盖质量 | `mcdc`（`cpu_backend` 的分派分支足够细，值得） | 复用 |
| `budget` | RAM/栈超预算 | 扩成 **flash / RAM / 峰值 workspace / 状态区 / 激活保活区** 五列 | 扩展 |
| `clocks` / `observability` | 实时性与可观测 | 改成 **n-API 计数**（算子调用数、分配次数、memcpy 字节）+ 真板周期计数 | 换语义 |
| `equations` | 公式↔代码一一对应 | **kernel 公式清单**（卷积/GEMM/softmax/LSTM 的数学式 ↔ 代码位置 ↔ parity 用例） | 换内容 |
| `combinations` / `domain` | 工况组合与运行域包络 | **census（模型×dtype×quant×tier）** + **`(模型, 板子) → 可行/不可行`判定表** | 换维度 |
| `blast` / `ports` / `symbols` | 变更影响面、端口一致性 | 照搬（尤其 `ports`：一个 tier 有实现就必须有 scalar 对照） | **部分复用** |
| `assume` / `anchor` / `regmap` / `matrix` / `subset` | 假设台账、文档锚点、寄存器映射、语言子集 | 与电机领域文档强耦合 | **丢弃** |

**infinfer 专属、foc 没有的三个门禁**（这是评估体系的增量）：

1. **`oracle`**：三层对比（scalar ↔ Python 参考解释器 ↔ 参考框架），容差按 dtype 分级（FP32 相对 1e-5；int8 逐位）。**双 oracle：ONNX/PyTorch 管新模型，TFLite/LiteRT 管存量资产**（两者本机都可用，MVP-V4/V5）。
2. **`kat`**：同一 blob 在 6 个目标上**逐位一致**——跨平台"结果一致"的唯一判据。
3. **`accuracy`**：量化模型相对 FP32 的**掉点上限**（如 int8 ≤1%、per-channel ≤0.5%，按模型定）——这是"量化确实生效"的行为级证据，也是本仓需要从第一天就具备的一条。
4. **`grad`**（C3 起）：解析梯度 vs 有限差分，相对误差 ≤1e-4；`no-grad` 内核必须显式标注。

> 一句话：**foc 的"物理模型对照"在推理库里对应的不是"和厂商库比快"，而是"和数学定义比对"**。厂商库只能当参照组，不能当金币（否则厂商库的 bug 会变成我们的判据）。
### 3.6 CI 分层：QEMU 不进 GitHub Actions

QEMU 在环的 job 单次动辄 10–40 分钟，放进 PR 路径会把反馈时间拖到不可用。foc 已经给了现成机制：`gates.py` 里有一份 **`LOCAL_ONLY` 名单**，而 `ci-policy` 门禁会**扫描 `.github/workflows/*.yml`，一旦发现 workflow 调用了 LOCAL_ONLY 的 gate 就报错**（`_ci_policy_violations`，`foc/.github/project/gates.py:136-162`）。照搬即可：

| 车道 | 跑在哪 | 门禁 | 目标时长 |
|---|---|---|---|
| **快车道（PR 必过）** | GitHub Actions | `build`（宿主 + 交叉**只编不跑**）、`apicontract`、`census`、`form`/`guard`、`deps`/`scaffold`、`oracle`（宿主）、`sanitize`（宿主 ASan）、`accuracy`（宿主）、`doc*`、`claim`、`ci-policy` | ≤ 10 分钟 |
| **本地车道（`LOCAL_ONLY`）** | 开发机 `workspace/qa/preflight.sh` | `kat`（6 目标 QEMU）、`bench`（真板）、`fvp`、`mutants`、`mcdc` | 分钟级到小时级，按需 |
| **夜车（可选）** | self-hosted runner（`[self-hosted, qemu]`） | 同上，但只跑 `schedule` + `workflow_dispatch` | 不影响 PR |

**证据桥（关键）**：本地跑的结论如何进入仓库？

1. 本地 `preflight.sh` 产出 `workspace/qa/results/<gate>-<commit>.json`；
2. 人工/脚本把**摘要**写进 `.github/project/claim-basis.json`，每条带 `{commit, host, date, local_only: true}`；
3. CI 只跑一个轻量 `evidence` 门禁：**证据的 commit 必须是 HEAD 的祖先，且不超过 N 天**——避免"拿旧证据过新代码"。

> 副产品：这也让"无 QEMU 的贡献者"不被阻塞——他们只需要 `oracle`（宿主）绿就能提 PR；`kat` 由维护者本地补。

### 3.7 ADR-004 · 互操作性：ONNX 只做"受限子集 + 推理侧"

**结论三句**：
1. **推理侧**：除 `tflite` 外，**新增 ONNX 作为第二输入格式**，但只承诺一个**可枚举的子集**（算子 × 属性 × opset 区间），**遇到未知算子硬失败并报节点名**（fail loud，不静默降级）。
2. **训练侧**：**不引入任何交换格式**（包括 ONNX）。C3 的梯度只存在于同一张图的 blob 里，参数交互用"权重段扁平打包"就够。
3. **闭源 `.exe` 退位**：ONNX 导入器是**开源的 Python 脚本**，它的正确性可以被 `gate/oracle` 直接验证（对 onnxruntime）——这是它相对三个 `.exe` 的**根本优势**。

| 做 | 不做 |
|---|---|
| ONNX 子集导入（**词表见下方实测结果**） | ONNX 全集、opset 全版本 |
| 静态 shape；动态维度只允许 batch=1 固定 | 动态 shape、Loop/If 控制流、自定义 domain |
| 导入 → **直接产 blob**（不引入第三份 IR） | 反向导出（训练图 → ONNX）；ORT Training |
| 用 onnxruntime / LiteRT 做参照组 | 把参照框架当金币（同 §3.5） |

**子集不能手写在文档里，必须是实测词表**。MVP-V10 用 4 个真实模型 + 1 个负向用例跑出了原型（产物 `workspace/_tmp/ops-map.json`）：

| 模型 | 前端 | 实际算子 | 判定 |
|---|---|---|---|
| MLP | TFLite int8 | `FULLY_CONNECTED ×2` | 子集内 |
| MLP | ONNX | `Gemm, Relu, Gemm` | 子集内 |
| Conv-Micro | TFLite int8 | `CONV_2D, MAX_POOL_2D, DEPTHWISE_CONV_2D, MEAN, FULLY_CONNECTED` | 子集内 |
| Conv-Micro | ONNX | `Conv, Relu, MaxPool, GlobalAveragePool, Flatten, Gemm` | 子集内 |
| 负向用例 | ONNX | `Einsum` | **OUT_OF_SUBSET**（指名 `Einsum@node0`，`exit=1`） |

规模：**25 个 kernel 名 ↔ 30 个 TFLite 名 ↔ 27 个 ONNX 名**。这张映射就是"子集"的定义，**应作为 `src/kernel/matrix.yml` 的算子词表种子**（INV-10 单一来源）。

**三条由 V10 实测得出、必须写进实现的规则**：
1. **判定单元是 `(op_type, attributes)`，不是 op 名**：ONNX 的 `Conv` 同时代表 conv 与 dwconv，靠 `group == in_channels` 区分——只看名字会把普通卷积误报成 dwconv（我原型就这么错了一次）。
2. **两个前端的清单必须分别维护**：同一个 MLP 在 TFLite 是 2 个节点（ReLU 被融合进 FC），在 ONNX 是 3 个。
3. **exporter 模式要锁**：torch 2.9+ 默认已切到 `torch.export` 路径，legacy TorchScript 路径产出的图不同（`Gemm` vs `MatMul+Add`）；同一条也适用 `TFLiteConverter` 的融合行为。

**为什么不让训练走 ONNX**：ONNX 本质是推理格式（ORT Training 是另一套扩展且 Torch-first）；嵌入式在线适应的参数交换只需"量化参数 + 张量数据"两段拼包，用 ONNX 只会把 1 个格式变成 2 个。

**为什么要做 ONNX 而不是只做 tflite**：PyTorch 用户的默认出口是 ONNX；而我们现有的 tflite 入口依赖闭源 `.exe`（§6 第 4 条）。开源导入器 + oracle 验证，是同时解决"可复现性"与"生态入口"的唯一低成本路径。

**前置事实（已核）**：本机系统 Python 只有 `numpy`，但 **`~/venv/build` 里 torch 2.12 / onnx 1.21 / onnxruntime 1.26 齐全**（MVP-V4 实测）。所以 P1.3 不需要从零建 venv，**只需把版本锁下来**（`requirements.txt`），并在干净机器上能用一条命令重建。

### 3.8 ADR-005 · 模型侧操作（裁剪/量化/蒸馏）归谁

**一句话：库只关心"结果格式"，不关心"过程"。**

| 操作 | 归属 | 库内的角色 |
|---|---|---|
| **量化（执行）** | **库内** | **必须**：int8/int16 kernel、per-tensor/per-channel、requantize、读 QDQ 参数（P2.3） |
| 量化（PTQ 校准，产生 scale/zero_point） | 离线工具 | 不实现；库只吃结果参数 |
| QAT（量化感知训练） | 训练侧 | **不做**（C3 之外） |
| 结构化剪枝 | 离线工具 | 不实现；剪完仍是**稠密图**，只是更小——运行时无感知 |
| 非结构化稀疏 | — | **第一版不做**：MCU 上收益小、kernel 复杂度高 |
| 蒸馏 | 离线/训练侧 | 不实现；产出是更小的学生模型 = 更小的 ONNX |
| 算子融合 / 常量折叠 / 布局变换 | 离线工具（可部分在导入器） | 可选，但必须由 `gate/oracle` 保证语义不变 |

**为什么这样分就无需付出额外代价**：
1. 剪枝与蒸馏**不改变运行时契约**——它们只产出一个更小的模型，所以"支持 ONNX 子集"已经自动覆盖了它们。把它们做进库里，等于让库去管它永远看不到的离线步骤。
2. 只有**量化**会改 kernel 契约（多一个 `dtype × quant` 维度），而这一维已经由 INV-4 / P2.3 承担。
3. 反而是**易用度**取决于另一个东西：用户需要的是"拿到模型 → 知道能不能跑 → 知道掉多少点"。所以给一个**模型准备流水线**（`workspace/qa/prep/`，Python，详见§3.10）：
   `子集检查（fail fast）→ 可选剪枝 → PTQ 量化 → 常量折叠 → blob`，每一步可跳过、每一步产出都过 `gate/accuracy`/`gate/oracle`。

**两个已由 MVP 定下的具体决定**：

| 决定 | 依据（`workspace/_tmp/MVP-VALIDATION.md`） |
|---|---|
| 量化参数的交换载体 = **QDQ**（`QuantizeLinear`/`DequantizeLinear`，含 per-channel `axis`） | 手搓 per-channel int8 QDQ 模型在 ORT 上跑通，`max\|diff\| = 1.9e-6` |
| ONNX 子集基线 = **opset 18** | torch 2.12 的导出器以 opset 18 为实现基线，请求 17 会走 ONNX C API 降级转换 |

**范围控制**：不做 NAS、不做蒸馏训练循环、不做 QAT、不做非结构化稀疏 kernel；这四条写进 `capabilities.rst` 的 out-of-scope。

### 3.9 ADR-006 · CCI 依赖地图：哪些值得引，引了放哪

**先立一条铁则**：`infra` 桶不是"开发期依赖"，而是"**消费者也必须接受的主包依赖**"——`_preparing_deps_links()` 把 `_infra` 并进 `CPP_DEPS`，`package_info()` 又写进 `components[_cpp].requires`，只有 GTest 被显式 `pop`。**所以参照/工具类一律不进任何桶。**

**调研方式（可复现）**：逐个查 `raw.githubusercontent.com/conan-io/conan-center-index/master/recipes/<name>/config.yml`（比网页 200/404 可靠——网页是 SPA，会对不存在的名字也回 200）。结果：**42 个候选里 38 个在 CCI**；不在 CCI 的恰好是全部 AI 加速库：`cmsis-nn`、`cmsis-dsp`、`cmsis-core`、`ne10`、`arm-compute-library`、`csi-nn2`、`nmsis`。

#### 层级 1：引入有实质意义（建议立即评估）

| 库 | 作用 | 抵掉的开发量 | 放哪 | 约束 |
|---|---|---|---|---|
| **`tensorflow-lite`**（CCI 有！）+ `flatbuffers` | 开源 TFLite 解析器 + 解释器 | **直接替掉闭源 `.exe`**，并多一个独立 oracle（**V5–V7 已验证**） | 只用工具侧（`workspace/qa/prep`） | 体积 MB 级、依赖重；**绝不进包** |
| **`xsimd`** | 一份 SIMD 代码覆盖 SSE/AVX/NEON/RVV | 把"每档手写一遍"压成"一份 + M-profile 两个特例"——直击我们最大的工作量 | `src/kernel/{x86,arm,rvv}` 的实现内部 | C++17；不支持 DSP/MVE；MCU 上退化 scalar |
| **`xxhash`**（优于 `crc32c`） | blob 完整性 / 版本配对校验 | 省掉自己写校验与格式指纹 | `cpp` 桶（需入白名单） | `crc32c` 有 SSE4.2 路径，xxhash 更便携 |
| **`tl-expected`** | `result<T,E>`，配 `-fno-exceptions` | 编排层错误处理可读性 | `cpp` 桶（header-only） | 只用 C++17 子集 |

> `tensorflow-lite` 在 CCI 是本次调研最大的发现：它把"要么用闭源 `.exe`、要么自己写 flatbuffer 解析"这个两难直接解了。与 ADR-004 互补：**ONNX 管新模型，TFLite 管存量资产**。
>
> **MVP 已验证（V5–V7）**：本机用 Keras → `TFLiteConverter` 造了一个 2496 B 的 int8 `.tflite`（magic `TFL3`），用官方 `schema_py_generated` 枚举出算子，用解释器跑出 golden，系统 python（仅 numpy）能验证。**两个细节必须写进实现**：① converter 会**融合算子**（`Dense+ReLU` → 2 个 `FULLY_CONNECTED`），所以 `subset` 必须枚举**文件里实际的算子**，不能按源图推断；② `tf.lite.Interpreter` 已被 TF 2.21 标记弃用，oracle 长期应锁 **`ai-edge-litert`**。

#### 层级 2：有明确用途但限定场景

| 库 | 用途 | 放哪 |
|---|---|---|
| `xnnpack` + `pthreadpool` + `cpuinfo` | SoC 后端（与 llama.cpp 同类的"可选引擎"） | `with_xnnpack`，SoC only |
| `eigen` / `openblas` | SoC 的 GEMM 后备（eigen 已在模板 `cpp` 桶，代码零引用） | SoC 后端，默认关 |
| `llama-cpp` | C4 的解码器路径 | `with_llama_cpp`，SoC only；`gaps.md` 写明"这部分性能属于 llama.cpp" |
| `kissfft` / `pffft` | 未来语音前端（MFCC）；第一版 out-of-scope | 记入 `guides/audio.rst` 的"未来选项" |
| `lz4` / `miniz` / `zstd` | 权重压缩（lz4 解压快、RAM 小，最可能适配 MCU） | 后议；blob 格式先留 `compression` 字段 |
| `benchmark`（Google Benchmark） | 宿主微基准（P2 档位对比） | **只能工具侧**（会污染依赖） |
| `cli11` | 工具侧 CLI 解析 | 工具侧 |
| `nanobind` | pybind11 的现代替代 | 不换（模板已用 pybind11） |

#### 层级 3：明确不用

| 库 | 不用的理由 |
|---|---|
| `simde` | 把 x86 intrinsics 翻译到其它架构——与"每档原生实现 + parity 验证"的策略相冲，性能不可控 |
| `ruy` / `gemmlowp` | TFLite 的上一代 GEMM，已被 XNNPACK 取代 |
| `nlohmann_json` / `rapidjson` / `toml11` / `yaml-cpp` | manifest 由 Python 读，C++ 侧读生成的 `.h` 就够 |
| `fmt` / `spdlog` | 给嵌入式增加体积；日志用 L0 的宏 |
| `span-lite` | INV-3 已把 kernel 契约定为 `(ptr, len)`，不需要 span |
| `mbedtls` / `doctest` / `protobuf`（除 onnx 工具侧） | 无场景 / 模板已定 |

**小结三句**：① 真正被"省掉开发"的是 **tensorflow-lite（替闭源工具）+ xsimd（替多档手写）**；② 两者都**不进包**（一个是工具，一个是实现内部）；③ 进 `cpp` 桶的只有 `xxhash`/`tl-expected` 这种**无依赖、header-only、能上 MCU** 的东西。

#### 但 CCI 的版本会落后于上游——已逐个核过

| 库 | CCI 最新 | 上游最新 | 差距 | 对策 |
|---|---|---|---|---|
| tensorflow-lite | **2.15.0** | TF 2.21 | **大（6 个版本）** | C++ 侧读模型可能不认新 converter 的算子 → **坚在用 Python 解析**（pip 的 TF 与 converter 同版本） |
| llama-cpp | **0.6.0** | v1.0.0（日常 `b####`） | **大** | 若做 C4：**自建 recipe 或 vendor 固定 commit**，不能靠 CCI |
| opencv | 4.14.0 | **5.1.0** | 大版本落后 | **我们不引入**（不在依赖图里）；它正是"CCI 跟不上就自己写 recipe"的例子（本机 `opencv/5.0.0` 先例） |
| onnx / onnxruntime | 1.20.1 / 1.24.4 | 1.23.2 / ~1.26 | 1–3 个小版本 | 无影响：我们只工具侧用 **pip**，不用 CCI |
| xsimd / xxHash / benchmark | 14.3.0 / 0.8.4 / 1.10.0 | **完全齐平** | 0 | 直接 `requires` |
| tl-expected | 1.2.0 | 1.3.1 | 1 个补丁 | 直接用，或 vendor 单头文件 |
| eigen | 5.0.1 | 5.x | 齐平 | 直接用（SoC 档，默认关） |
| flatbuffers | 25.12.19 | 当前 | 齐平 | 直接用（仅工具侧） |
| **CMSIS-NN / ncnn** | **无配方** | v8.0.0 / 20261020 | 无 | 自建 recipe（CMSIS-NN）或不引入（ncnn 只做参照） |

**由此得出的一条决策规则**（写进 `capabilities.rst` 与 `deps` 门禁）：

> **引入一个依赖前先核两件事：CCI 有没有、版本是不是我们真需要的那个。**
> 若"要用 + CCI 落后且落后点正好是所需特性" → **在 `workspace/conan/recipes/` 自建 recipe**（照 `opencv/5.0.0` 的做法），并把版本钉死。
> 若"只是用其最新行为" → 换成 pip wheel（工具侧）或 vendor 固定 commit。

### 3.9.1 ADR-007 · L2 张量描述符与工作区回退（`95dae4b` 后第一块 L2）

**问题**：INV-3 把 shape 从 L1 签名里赶走，但没有任何东西把 shape **接住**。`matrix.yml` 把 conv/dwconv 移进 `composed` 之后，谁来做 gather、谁来算输出尺寸、临时缓冲从哪来，都还没有落点。

**决策一：shape 只有一个描述符，且步长不存。**
`infr_shape{ dims[4], rank, elem_count }` + `infr_tensor{ data, shape, dtype, quant }`，偏移由 `infr_shape_offset` 现算（行主序、越界即错）。**不存 stride**：存下来的 stride 就是同一事实的第二份真相，而"偏移表混用字节与字"是参考实现中出现过的一类问题（见 `workspace.h` 的 note）。
- 副作用：不支持广播/转置视图——这是有意的，v0.1 只承认连续张量；非连续布局留给"blob 里的 layout 字段 + 一次显式 copy"，而不是让每个算子自己处理 stride。

**决策二：`elem_count` 用 32 位并在 64 位里累乘。**
65536⁴ 在 32 位里恰好回绕成 0，看起来像"空张量"而不是"装不下"。所以乘积在 `uint64_t` 里累加、超过 `UINT32_MAX` 直接报参数错误。**零长度轴一律拒绝**：空张量是图构造错误，放过去就会在下游变成一次静默的空操作；唯一允许"空"的地方是传给 kernel 的归约长度（那不是 shape，`sum` 的长度 0 就是 0.0）。

**决策三：工作区必须能回退。**
`infr_workspace_mark/release` 是 L2 算子存在的**前提**：conv 要把一个 gather 缓冲借出来、用完还回去，否则 `EVAL` 会随图的执行单调长胖（INV-8）。`release` 只接受 `≤ used_bytes` 的 mark——把游标往前挪等于把已经发出去的字节再发一次，所以是错误返回而不是截断。

**为什么现在做而不是等 conv**：这三件事是 conv/pool/mean/blob 的共同地基，且都能**独立测**（`contract_tensor_shape.cpp` 7 例、`contract_workspace_rewind.cpp` 3 例，34/34 全绿）。先钉地基，再让 `composed` 有东西可组合。

### 3.10 生成器往哪里放（回应"不想 repo 被动得面目全非"）

**问题**：我上一版把 `tools/prep/` 放在根目录，等于给仓库加一个新顶层条目。而模板已经把"额外目录的吸收点"设计好了（`test_package/test/{unit,stress,python}`），所以正确做法是**能吸收就吸收，不能吸收就放 `workspace/`**。

**核心判断：生成 ≠ 验证。** 先把两件事拆开：

| 动作 | 频率 | 谁做 | 放哪 | CI 需要吗 |
|---|---|---|---|---|
| **生成** golden（ONNX → blob → ORT 跑出 expect） | 低频（换模型/换判据） | 维护者本机 | **`workspace/qa/prep/`** | ❌ **不需要** |
| **验证** golden（运行时输出 vs 已入库 expect） | 每次 PR | `gate/kat` / `gate/oracle` | `test_package/resources/kat/` + 测试代码 | ✅ 需要（但不需 torch/ORT） |

三重好处：
1. **仓库根目录不多一个条目**（符合你的忌讳，也与 foc 的 `workspace/audit`、`workspace/manual` 同构）；
2. **CI 不需要装 torch/onnxruntime**（快车道更快更稳，`gate/oracle` 退化成纯数值比对）；
3. **INV-6 仍成立**：新鲜 clone 不装任何 Python ML 依赖也能跑完所有测试。

**如果团队坚持工具入库**，唯一可接受的落点是 **`test_package/test/python/prep/`**：
- `scaffold-paths.txt` 只列了 `test_package/CMakeLists.txt` 与 `conanfile.py` 两个文件 → 新文件不产生 drift；
- 模板本就约定"`test/python/requirements.txt` 存在时 CI 安装依赖" → 天然支持；
- 但语义上它是"测试目录里的工具"，不如 `workspace/` 干净。

**新增不变量 INV-11（根目录白名单）**：仓库根只允许模板给定条目 + `include/ src/ test_package/ benchmark/ docs/ workspace/`。任何新工具默认进 `workspace/`；若"CI 必须执行"，先问一句：**能不能改成"产物入库 + CI 只验证"？** 能，就不要加目录。

test_package/resources/kat/
├── manifest.json                 # 唯一索引：{id, source, shape, dtype, quant, tol, sha256}
├── k1_mlp3/{model.blob, input.bin, expect_fp32.bin, expect_int8.bin}

```

**4）判据（容差写死在 manifest 里）**

| dtype | 与 ORT 比 | 跨目标比 |
|---|---|---|
| FP32 | `max_rel ≤ 1e-5` 且 `max_abs ≤ 1e-6` | **逐位相等** |
| INT8 / INT16 | 逐位相等（MAC 顺序固定）；否则 ≤ 1 LSB 且必须写进 gaps | **逐位相等** |

**5）测试接线**

- 文件：`test_package/test/unit/graph_kat_<id>.cpp`，一个 case 一个；
- 路径：用 `RESOURCES_PATH` 宏拼接，不写绝对路径；
- 失败信息必须含：case id、第几个元素、期望/实际、绝对/相对误差（用 hex 或整数打印，**不得用 `%f`**）。

**6）验收命令**

```bash

python3 .github/misc/gates.py oracle   # 快车道（宿主）
python3 .github/misc/gates.py kat      # LOCAL_ONLY（6 个 QEMU/宿主目标）
```

**7）边界（故意不做）**

- **不用 `.tflite` 做 KAT 输入**（避开闭源工具）；tflite 只在"兼容性抽查"里作第二输入；
- 不在 KAT 里做"训练后再推理"（那是 P6）；
- 不用厂商库产 golden（否则厂商 bug 变判据）。

**8）常见错误（写下来防止 agent 踩）**

- 把 golden 生成逻辑写进 C++ 测试 → 变成自证；必须 Python 独立产；
- 用 `float` 格式化打印比对结果 → 精度不可复现；
- `manifest.json` 里没有 `sha256` → golden 被改也不会被发现；
- **按源图算子推断子集** → converter 会融合算子（V5 实测），必须以文件为准；
- 把 torch/TF/ORT 引入 `gate/oracle` 的 CI 路径 → V7b 已证明验证只需 numpy。

## 6. 明确不做（防止"解决问题的速度不及制造问题"）

1. **不按 audit 的"果"逐条打补丁**：先建 P1 的骨架，再回头收 3 个缺陷。
2. **不做"全平台迁移适配"**：第一版只承诺 6 个 tier（scalar/x86/arm-neon/arm-m-dsp/arm-m-mve/rvv1.0）；CSI-NN2/PULP-NN 只以插件形式验证可行性。
3. **不引入运行期动态分配**（MCU 路径）；SoC 路径可以用 allocator，但必须由 backend 注入，且 `gate/budget` 记账。
4. **不继承闭源工具链**：`tools/*.exe` 是参考仓的资产；新仓从第一天就只有源码通道（ONNX 子集导入 + 手搓 blob），不存在"要么源码化要么写 gaps"这个选项。
5. **不让 README 手写数字**：所有矩阵由 `.github/project/claim-basis.json`（原始数据在 `workspace/qa/results/`）生成。
6. **不在 P0–P2 期间改 Gallery**：等 M5 再一次性改，避免文案反复。
7. **不把任何厂商 NN 库当作"某平台能跑"的前提**（NMSIS/CSI-NN2/CMSIS-NN 只能加速，不能承重）。
8. **不支持需要定制 GCC 的芯片**（如中科蓝讯）；平台矩阵只收纳 house toolchain 能出产物的板子（INV-7）。
9. **不在主线用拿不到 RVV 1.0 的 train**：RV 主线固定 `14.3.rel1`；要支持老板子就另开一个 `12.3` 兼容 job，且只承诺 scalar 档。
10. **不在 MCU 上承诺 LLM**：C4 只在 SoC（≥ 64 MB RAM）上承诺；MCU 只承诺 C1/C2。
11. **不做通用深度学习框架**：只支持"能塞进目标内存"的模型族；不承诺任意图与动态 shape。
12. **不为"多态"而多态**：C3/C4 必须在 C1/C2 交付后按需求启动，不得并行开工。
13. **不做通用训练框架**：C3 只到"在线适应"（§2.3 边界表）；不支持 QAT、通用 autograd、数据集训练。
14. **不做 ONNX 全集**：只做可枚举子集 + 推理方向；训练侧不引入任何交换格式（ADR-004）。
15. **不为一个脚本新增顶层目录**：根目录白名单见 INV-11；工具一律进 `workspace/`（生成≠验证，§3.10）。
16. **不做专利侵权判断 / 不出法律意见**：`compliance/patents/` 只维护**检索台账**（字段完整、有原文、有复核人），结论由法务/专业机构出（§9.8）。

### 11.1 四处必须记住的纠正（本计划早期版本的洞）

1. **模板门禁只有 5 条，不是 21 条；而且 `all` 只聚合 3 条。**
